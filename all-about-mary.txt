1. What Is AstroScan?
AstroScan is a full-stack, machine learning-powered stellar anomaly detection system that ingests real photometric data from NASA space telescopes, applies unsupervised learning to model 'normal' stellar behaviour, and automatically flags unexplained deviations in light curves - classifying them as planetary transits, stellar flares, instrument noise, or genuinely anomalous signals.

In Andy Weir's Project Hail Mary, humanity discovers the alien organism Astrophage by noticing an inexplicable anomaly in solar energy measurements. AstroScan operationalises this exact idea - but with real telescope data, real ML, and a real deployable system. You are literally building the Hail Mary's detection algorithm.

The system has three major pillars:
• Pillar 1: Data Engineering - automated ingestion and preprocessing of NASA Kepler/TESS FITS files via public APIs
• Pillar 2: Machine Learning - LSTM autoencoder trained on 50,000+ light curves to model normal stellar flux, combined with a CNN classifier for signal typing
• Pillar 3: Full-Stack Product - a React dashboard with an interactive star map, anomaly timeline, spectral plots, and a FastAPI backend with Docker deployment on AWS

2. Real-World Usefulness & Applications

3. What Makes AstroScan Novel?
Most student ML projects use Titanic, MNIST, or house price datasets. AstroScan's novelty comes from several dimensions:

3.1 Real, Messy, Scientific Data
NASA's FITS files are notoriously difficult to work with. They contain binary headers, irregular time sampling, instrument systematics, and missing cadences. Processing this data correctly is itself a significant engineering achievement that most students never attempt.
3.2 Multi-Modal ML Architecture
The combination of an LSTM autoencoder (for temporal anomaly scoring) fed into a CNN classifier (for waveform-shape-based signal typing) is a genuinely sophisticated two-stage architecture. This is not a tutorial model - it mirrors real research pipelines published in journals like The Astrophysical Journal.
3.3 The 'Unknown Signal' Category
Most anomaly detectors classify into known categories. AstroScan's fourth class - 'Unknown / Unexplained' - captures signals that don't match any learned template. This is the scientifically interesting category, and building it requires careful calibration of confidence thresholds and ensemble methods.
3.4 Live Interactive Dashboard
The React frontend with a real D3.js star map, zoomable light curve viewer, and anomaly confidence scoring moves this beyond a Jupyter notebook into a deployable product. Very few student projects reach this level of end-to-end polish.
3.5 Thematic Coherence
Every design decision - from the dark UI colour palette, to the naming conventions (signals are called 'Contacts', anomalies are 'Events'), to the fictional Astrophage category - is consistent with the Project Hail Mary universe. This thematic coherence makes the project memorable and demonstrates product thinking.

6.2 Questions You Will Be Asked - And How You'll Crush Them

'Walk me through your ML architecture'
LSTM autoencoder learns temporal patterns. Reconstruction error = anomaly score. CNN then classifies waveform shape. Two-stage pipeline, show diagram.
'Why not just use threshold-based detection?'
Thresholds are static and brittle. Stars have different intrinsic variability. The autoencoder learns per-star baselines. Mention that this matches real NASA approaches.
'How did you handle class imbalance?'
Anomalies are rare (~1-5% of windows). Used weighted loss, SMOTE on training data, and adjusted decision thresholds. Show precision-recall curves.
'How did you deploy this?'
Docker containers for API and model server, deployed on AWS EC2. GitHub Actions CI/CD runs tests and auto-deploys on merge. API documented with auto-generated FastAPI docs.
'What would you improve?'
Transformer-based architecture (like Informer) for longer context windows. Active learning loop where astronomers can label new anomalies and retrain. Shows you've thought beyond the project.

9. Frontend Design - The Project Hail Mary Aesthetic

The AstroScan dashboard is designed to feel like mission control software from the novel - not a generic SaaS dashboard. Every design decision reinforces the space-science theme.

9.1 Colour Palette

Deep Space Black (#0A0B14)
Primary background - mimics the void of space. Never pure #000000.
Nebula Purple (#4B3FA0)
Primary accent - console displays and scanner readouts in sci-fi often use blue-purple.
Bioluminescent Teal (#0F9B7A)
Confirmed safe signals / transits - green-teal suggests 'known, benign'.
Alert Amber (#C87C1A)
Anomaly alerts - warm amber for 'attention required' without red's false alarm connotation.
Astrophage Red (#8B2020)
Unknown / unexplained contacts - deep red for genuine unknowns.
Star White (#E8E4F8)
Primary text - slightly purple-tinted white feels cold and cosmic.
Console Gray (#2A2B40)
Panel backgrounds - one step lighter than the void.

9.2 Typography
• Display / Headers: Space Grotesk or Orbitron (Google Fonts) - geometric, technical, sci-fi without being cliché
• Body / Data: JetBrains Mono - monospace for all numerical data (flux values, timestamps, coordinates) feels like a real scientific instrument
• UI Labels: IBM Plex Sans - clean, technical, used in real NASA mission interfaces

9.3 Key UI Components

The Stellar Map
A D3.js force-directed or equirectangular projection of the observable sky, with each monitored star rendered as a pulsing dot. Colour indicates status: white for clean, amber for anomalous, red for unknown. Clicking a star opens its detail panel. This is the centrepiece of the dashboard - no other student project has anything like it.
Light Curve Viewer
An interactive SVG plot (using D3 or Recharts) showing flux over time for the selected star. Anomaly windows are highlighted with a semi-transparent amber overlay. Users can zoom and pan. A reconstruction error subplot below shows the autoencoder's confidence per window.
Contact Alert Feed
A real-time scrolling feed (polling the API every 30 seconds) showing new anomaly detections. Each alert has a severity badge, star ID, coordinates, and a one-line ML classification reason. Styled like mission control telemetry - monospace font, subtle scan-line animation.
Signal Classification Panel
When a star is selected, this panel shows the CNN classifier's output as a horizontal confidence bar for each of the four classes: Planetary Transit, Stellar Flare, Instrument Noise, and Unexplained Contact. Bars animate in on load using Framer Motion.
Mission Statistics Header
A persistent header strip showing: Stars Monitored, Contacts Detected Today, Unexplained Contacts (the scary number), and Model Last Retrained. All numbers count up with a ticker animation on page load - deeply satisfying.

9.4 Motion & Micro-interactions
• Stars on the map pulse with a slow CSS animation - frequency increases when anomalous
• New alert cards slide in from the right with a subtle glow border in the alert colour
• The light curve plot's anomaly overlay fades in after the baseline renders - visual storytelling
• Page load: stats count up from zero over 1.2 seconds using a custom easing curve
• Hover on any star: a tooltip appears with Star ID, magnitude, constellation, and anomaly count

10. Suggested Build Plan


Environment setup. Download 5,000 Kepler light curves via Lightkurve. EDA in Jupyter. Understand FITS file structure. Build preprocessing pipeline (detrend, normalise, window).

Train LSTM autoencoder baseline. Evaluate reconstruction error distribution. Tune threshold. Validate against known exoplanet transits in Kepler catalogue.

Build CNN classifier for signal typing. Create labelled training set (transits from Kepler catalogue, flares from published datasets). Train, evaluate, iterate.

FastAPI backend. Endpoints: /stars, /stars/{id}/lightcurve, /stars/{id}/anomalies, /contacts, /hail-mary. PostgreSQL schema. Redis caching. Dockerise.

React frontend. Star map with D3.js. Light curve viewer. Alert feed. Classification panel. Dark theme, typography, motion.

Deploy to AWS/Railway. GitHub Actions CI/CD. Write README, architecture diagram, API docs. Record a demo video. Polish everything.
